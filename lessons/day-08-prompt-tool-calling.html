Prompt 与工具调用：模型怎么挑工具、参数错了谁兜底

模型只会输出文本，工具调用是它碰世界的唯一方式：模型负责选哪个工具、填什么参数——这两次选择都是在算概率；后端负责解析、校验、执行、把结果拼回上下文。工具定义进提示当检索信号，JSON Schema 框住参数形状，strict 模式保证形状合规，但语义对不对只能由后端校验。参数传错要分层兜底、错误回填给模型重试；工具太多要按需加载。模型是总会传错参数的客户端，防呆必须做在服务端。

2026-11-08 · 约 18 分钟
01 为什么需要工具

模型只会出文本，工具是它碰世界的手。

模型只会输出文本：它算的是下一个 token 的概率，再大的模型也碰不到真实世界——查不了天气、订不了机票、改不了数据库。工具调用就是给模型装手：模型只负责说“调哪个工具、传什么参数”，真正执行的是你的后端代码。

这条分工线是安全设计的起点：模型输出的只是一段结构化文本——工具名加一段 JSON 参数。后端拿到它要先解析、再校验、再执行，最后把结果拼回上下文，模型接着生成回答。模型从不直接碰数据库和 API。

  • 模型只生成调用意图（工具名 + JSON 参数），执行永远在后端。
  • 工具返回的结果拼回上下文，变成下一轮生成的 observation。
  • 这条分工线决定了安全边界：校验必须长在后端，不在模型嘴里。
02 模型怎么选工具

工具清单进提示，选工具就是算概率。

工具清单是每次请求的一部分：每个工具的名字、描述、参数 JSON Schema 都被序列化进提示，模型在回答前先看到全部可选工具。它选哪个工具，本质上是在工具名 token 上算概率——描述与用户意图越匹配，该工具名的概率越高。

所以工具描述不是文档，是检索信号：名字要像动词短语，描述第一句就要写清“什么时候用、不用什么时候用”。两个功能重叠的工具，模型只能靠描述区分——描述写得含糊，选错就是必然。

  • 工具定义进提示：名字 + 描述 + JSON Schema，占用上下文、按 token 计费。
  • 选工具 = 在工具名上算概率，描述写得越像检索关键词，挑得越准。
  • 模型也可以决定不调工具：该调没调、不用却调，都是常见失效。

03 参数怎么填

JSON Schema 是填空题的格子，只框形状不框语义。

选定工具后，模型按 JSON Schema 逐 token 生成参数：哪个字段必填、哪个是字符串、哪个只能取枚举值，schema 把填空题的格子先画好。OpenAI 的 strict 模式更进一步，用约束解码保证输出一定符合 schema，形状错误基本绝迹。

但 schema 只框形状，不框语义：order_id 是字符串没错，可它指的订单根本不存在；date 格式对了，可那天是过去。模型填参数时看不到你的数据库，它只是在猜“什么样的值最可能出现”。语义对不对，只能由后端在执行前校验。

  • Schema 框住类型、必填、枚举；strict 模式保证形状一定合规。
  • 语义校验不在模型手里：不存在的 ID、过期的日期，schema 拦不住。
  • 参数值是模型逐 token 猜出来的，不是查出来的——要当不可信输入。
04 工具调用是练出来的

先出工具名、再出参数，是微调练成的格式。

基座模型天生不会调工具：它只会续写文本，工具调用的格式（先出工具名、再出 JSON 参数、等结果再继续）是后天练出来的。做法是在微调数据里放大量“用户问题 → 工具调用 → 结果 → 回答”的完整轨迹，让模型把这套格式学成条件反射。

Toolformer 更进一步，用自监督代替人工标注：模型自己在文本里提议 API 调用并真的执行，只保留那些让后续文本更容易预测（loss 下降）的调用来微调。GPT-J 6.7B 配上计算器、搜索等 5 个工具，零样本任务上常常超过大得多的模型——工具的价值，就是让后面的 token 更好算。

  • 工具调用是微调练出的格式，不是基座模型天生的能力。
  • Toolformer：只保留让后续文本 loss 下降的调用，模型自己学会何时调工具。
  • Gorilla：微调 LLaMA-7B 写 API 调用，在 1645 个 API 上准确率超过 GPT-4。
05 参数传错怎么兜底

五种死法，分四层接住。

参数传错有五种死法：JSON 解析失败、调了不存在的工具、缺必填字段、类型不对、值在语义上不存在。前四种是形状问题，schema 和 strict 模式能拦；最后一种最常见也最危险——格式全对，查无此人，只能靠业务校验。

兜底要分层：解析层修 JSON 或判失败、schema 层校验形状、语义层查库核对存在性与权限、执行层设超时与重试。任何一层拦下，都不要只回一句“400”——把错误写成给模型的提示：错在哪、该怎么改、今天是几号。错误信息是模型的反馈通道，写得越具体，模型自我修正的成功率越高。

  • 五种死法：解析失败、工具不存在、缺字段、类型错、语义不存在。
  • 分层兜底：解析 → schema → 语义 → 执行，每层只拦自己能判断的错。
  • 错误要回填给模型重试：写清错因与修正方向，上限 3 次，超了转人工。

06 并行与串行

一次调几个，看调用之间有没有依赖。

一轮里模型可以一次发出多个工具调用：查北京天气和查上海天气互不依赖，并行调能省一轮往返；但“先查订单再退款”有依赖，必须等 observation 回来才能调下一个。并行还是串行，不由后端决定，由依赖关系决定——模型要自己判断哪些调用能一起发。

后端要做的是把这套语义接住：并行调用要并发执行、按 call_id 对齐结果；串行调用要等上一轮 observation 进上下文再发下一轮。ReAct 循环的每一轮都是这个结构：模型提议、后端执行、结果回填、模型再提议——工具调用是循环的 Action，observation 是循环的燃料。

  • 无依赖的调用可并行：一次发多个，按 call_id 对齐结果。
  • 有依赖的必须等 observation 回来：先查后改，不能一次发完。
  • 工具调用就是 ReAct 循环里的 Action，observation 是下一轮的输入。
07 工具太多会怎样

清单越长越贵、越容易挑错，按需加载。

工具不是越多越好：每个工具定义几百 token，50 个工具光清单就上万 token，又贵又挤占真正的内容；选择空间一大，模型挑错的概率也跟着涨——第 5 天讲过，上下文越长，有效信息越容易被稀释，工具清单也一样。

做法是按需加载：平时只给模型一个“搜工具”的元工具或检索器，需要时再把具体工具定义取回来；或者按场景分组，客服场景只挂客服工具。Gorilla 的做法与此同构：先检索相关 API 文档，再让模型在小范围里选——选错率随候选集缩小而下降。

  • 每个工具定义占几百 token：清单越长越贵、选择越难。
  • 按需加载：检索路由或 tool search，用时再取定义。
  • 按场景分组挂工具，不用的工具不要出现在提示里。
08 常见坑与落地

模型是总会传错参数的客户端，防呆做在服务端。

第一，把模型当可信调用方：参数不校验就执行，等于把 SQL 拼接交给用户输入——模型的参数永远是不可信输入，校验、权限、确认必须长在执行层。第二，错误信息写给人看不写给模型看：“参数错误”四个字模型改不对，要写“date 必须是 YYYY-MM-DD，今天是 2026-11-08”。

第三，无限重试：模型改不对时反复调同一工具，账单和延迟一起炸——重试要设上限、加退避、超了转人工。第四，工具描述写给人看：名字含糊、描述只写功能不写边界，模型选错是迟早的事。后端类比：工具调用就是 RPC，工具定义是 OpenAPI，模型是那个总会传错参数的客户端——所有防呆都要做在服务端。

  • 模型参数 = 不可信输入：校验、权限、确认长在执行层。
  • 错误信息写给模型看：错因 + 修正方向 + 当前事实。
  • 重试设上限、加退避；工具描述第一句写清使用边界。

自测

线上 Agent 查订单时，模型把 order_id 填成了一个不存在的编号。按本课讲的分层兜底，后端最该怎么做？

A. 直接执行查询，让数据库返回空结果，再由模型自己猜一个编号
B. 执行前按业务规则校验编号是否存在，把“编号不存在，请向用户确认正确编号”作为 observation 回填给模型重试 ✓
C. 关掉 strict 模式，让模型自由发挥格式，少一次校验
D. 默默把编号改成最近的一单，继续执行，别打断用户
解析：order_id 格式全对、语义不存在，schema 拦不住，只能由语义层在执行前校验。拦下后要把错因写成给模型的提示回填，让它向用户确认后重试；直接执行、关校验、默默改值都会把小错放大成事故。
证据

论文与文章

  • Toolformer: Language Models Can Teach Themselves to Use Tools（Timo Schick 等，NeurIPS 2023 2023）
    支持：自监督学工具使用：模型自己提议 API 调用并执行，只保留让后续文本更容易预测（loss 下降）的调用来微调；GPT-J 6.7B 配 5 个工具，零样本任务上常超过更大的模型。
    边界：工具调用各自独立生成，不能串联多步、不能交互式追问，也不考虑调用成本。
  • Gorilla: Large Language Model Connected with Massive APIs（Shishir G. Patil 等，NeurIPS 2023 2023）
    支持：微调 LLaMA-7B 写 API 调用，在 1645 个 API 的 APIBench 上功能准确率超过 GPT-4；配文档检索后能适应文档变化、减少幻觉。
    边界：结论基于 APIBench 的 ML API 场景；准确率指功能正确，参数语义仍需服务端校验。
  • Function calling（OpenAI，OpenAI 平台文档 2023）
    支持：工具调用是五步循环：定义工具（JSON Schema）→ 发请求 → 模型返回 tool_calls → 应用执行 → 结果作为 tool call output 拼回；strict 模式保证参数严格符合 schema，tool_choice 控制是否允许调用。
    边界：在线文档随版本更新，strict 模式与 tool search 等能力以当前文档为准。
