AI AGENTS 深入学习 · 第 13 天

评估与观测：先把好坏变成数字，再把每次运行变成黑匣子

Agent 是非确定性系统——同一输入两次运行可能走不同轨迹、得出不同结果。感觉、演示视频、一次成功都不能证明它好。评估是把“好”拆成可重复测量的数（成功率、成本、延迟），观测是把每次运行的每一步都记下来，让失败可复现、可定位。没有这两样，改 prompt 就是蒙着眼睛调参。

2026-11-13 · 约 18 分钟
01 为什么是评估与观测

一次成功证明不了什么，十次里成功九次才算。

模型本身是非确定性的：同一 prompt、同一温度，两次采样可能走不同的工具路径；工具返回也随时间变。一次演示成功，证明不了什么；十次里成功九次，才算有点把握。

更麻烦的是“好”有三个维度：做对了没有（成功率）、花了多少钱（成本）、等了多久（延迟）。三者互相牵制：多采样提成功率，账单和延迟一起涨。评估就是把这三维同时钉在纸上，观测就是每次运行都留下可查的账。

  • 单次成功 ≠ 系统可靠：同一任务要跑多次，看分布不看单点。
  • 成功率、成本、延迟三维一起看，只看一维会被另外两维偷袭。
  • 评估回答“现在有多好”，观测回答“坏在哪一步”。
02 三维指标

成功率、成本、延迟：三维一起钉住，才叫好。

成功率是最容易被误读的数：分母是什么？是任务数，还是步数？只统计“跑完没报错”还是“结果真对”？定义不写清，两个 80% 完全不可比。成本要按任务摊：一次任务的成本 = 步数 × 每步 token × 单价，多一步循环就多一份钱。延迟要看分布：p50 漂亮、p99 难看，说明少数任务在死循环里烧钱。

三维之间是跷跷板：想提成功率，可以加自我验证、加重试、换大模型——每一招都同时抬成本和延迟。工程决策不是“越高越好”，而是先定预算线（单次任务最多花多少钱、最多等多久），再在线内把成功率推到头。

  • 成功率先写定义：什么算成功、谁来判定、分母是什么。
  • 成本按任务摊：步数 × token × 单价，循环次数是最大的乘数。
  • 延迟看 p99 不看平均：长尾里藏着死循环与重试风暴。
03 成功的三层判定

怎么判定一次运行成功了：三档工具串联用。

判断一次运行成没成功，有三档工具，由严到松。第一档断言：答案与标准答案逐字比对，精确但死板——正确换个说法就判错。第二档程序化检查：不看答案文本，看世界状态——文件写好了没有、数据库里那行改了没有、仓库测试通了没有。SWE-bench 就是这档：补丁只有让仓库自己的测试通过才算数。

第三档打分：开放式任务没有唯一答案，只能按评分标准打分，人打最准但最贵，模型打便宜但自带偏差（第 6 节讲怎么校准）。三档不是三选一，是串联：断言拦低级错，程序化检查验真结果，打分补开放题。只用一档，漏掉的恰恰是另一档能抓的错。

  • 断言：快而严，但正确换说法会被误杀。
  • 程序化检查：验世界状态不验文本，是 Agent 评测的主力。
  • 打分：补开放题，但打分者本身也要被评测。

04 基准怎么选

三把公开的尺子，各量各的东西。

公开基准是现成的尺子，但每把尺子量的东西不一样。SWE-bench 量的是修真实 GitHub issue：2,294 个任务，补丁要让仓库测试通过才算数，发布时最强的 Claude 2 只解决 1.96%。GAIA 量的是通用助手：466 道人工出的题，答案唯一可验证，但要上网、读文件、多步推理，人类 92%，带插件的 GPT-4 只有 15%。WebArena 量的是在自建网站上完成任务：812 个任务，GPT-4 成功率 14.41%，人类 78.24%。

用基准要先看它在量什么：三把尺子量的都是“模型 + 支架 + 工具”整个系统，不是模型单体。同一把尺子分数涨了，可能是支架变好了，不是模型变强了。更要紧的是，基准分是别人的任务，不是你的任务——它能帮你选模型，帮不了你证明你的 Agent 在你自己的任务上行不行。

  • SWE-bench：修真实 issue，程序化验测试，2,294 任务。
  • GAIA：466 道通用助手题，答案唯一，人类 92% vs GPT-4 15%。
  • 基准量的是整个系统；选模型可以，证明自己的业务不行。
05 自己的评测集

自己的评测集：进版本库、进 CI、当回归门禁。

真正能证明你的 Agent 行不行的，是你自己的评测集：从真实用户请求里挑 50–200 条有代表性的任务，每条写清输入、期望结果、判定方法（断言还是检查还是打分）。它是产品资产，要像代码一样进版本库、写进 CI：每次改 prompt、换模型、动工具，先跑一遍评测集，分数掉了就拦住上线——这就是回归门禁。

建集有两条铁律。第一，测试集与调参集分开：调 prompt 时看过的题不能再当考试题，否则分数是调出来的，不是测出来的——等于开卷考试还抄了答案。第二，样本量决定可信度：20 条题上从 62% 涨到 81%，可能只是运气（20 条的波动就有 ±20 个点）；想分辨 5 个点的真改进，至少要上百条。

  • 评测集 = 真实任务 + 期望结果 + 判定方法，进版本库、进 CI。
  • 调参集与测试集分开：看过的题不能再当考试题。
  • 样本量决定可信度：20 条的涨幅可能是运气，百条起步才谈改进。
06 LLM-as-judge

模型当评委：能用，但要先校准。

开放式任务只能靠打分，人工打分贵，模型打分（LLM-as-judge）就成了主力。Zheng 等人的论文测过：GPT-4 当评委，与人类专家的意见一致率超过 80%，和人类之间互相的一致率差不多。但评委自带三类系统偏差：位置偏差（先看到的答案占便宜）、啰嗦偏差（长的答案占便宜）、自我偏爱（像自己风格的答案占便宜）。

所以评委本身也要被评测，这叫校准：先让人给一小批样本打分，再让模型评委打同一批，算两者的一致率——一致率不到人类互相的一致率，就不能信；还要双向跑（两个答案换位置各判一次，只有两次都赢才算赢）、写死评分标准、把评委换成与被评系统不同家族的模型。没校准过的评委分数，和没验过的模型输出一样不可信。

  • 评委三类偏差：位置、啰嗦、自我偏爱，都是系统性的。
  • 校准：先拿人类标签测评委的一致率，够格了再用。
  • 双向跑 + 写死标准 + 换家族评委，三招压偏差。
07 观测

观测：把每次运行记成一条可查的黑匣子。

评估告诉你“现在有多好”，观测告诉你“坏在哪一步”。做法是把每次运行记成一条 trace：整条 trace 是一次任务，里面每个 span 是一步（一次模型调用、一次工具调用），span 上记着输入、输出、耗时、token 数、成本、错误。线上出问题，先按 trace_id 把那次运行整条捞出来，再看哪个 span 耗时最长、哪步 token 烧得最多、哪次工具调用报错——不用猜。

记什么有讲究：输入输出要记（否则无法复现），但密码、密钥、用户隐私要脱敏；token 与成本要按 span 记（才能定位哪一步在烧钱）；错误与重试要记（才能看到重试风暴）。量大了要采样：全量记便宜的小任务，采样记贵的长任务。观测不是事后翻日志，是系统上线前就布好的线。

{
  "trace_id": "tr_9f2c",
  "spans": [
    {"name": "llm.plan",   "ms": 1820, "tokens": 2400, "cost": "¥0.03"},
    {"name": "tool.search", "ms": 640,  "tokens": 0,    "cost": "¥0.00"},
    {"name": "llm.write",  "ms": 3100, "tokens": 5100, "cost": "¥0.07"}
  ]
}
  • trace = 一次任务，span = 其中一步，span 上记耗时、token、成本、错误。
  • 按 trace_id 捞整条运行：定位哪一步慢、哪一步贵、哪一步错。
  • 隐私脱敏 + 采样：全量记小任务，采样记长任务。
08 组合与落地

闭环跑起来，再防指标被玩坏。

评估与观测合起来是一条闭环：跑评测集 → 看失败的 trace → 把失败归类（是工具选错、是上下文丢了、是循环打转、是判定太严）→ 一次只改一个地方 → 再跑评测集，看分数与成本、延迟一起动没动。改 prompt、换模型、加工具，都是这条环上的一步；没有环，每次改动都是赌。

最后一条红线是古德哈特定律：指标一旦变成目标，就不再是好指标。成功率写进 KPI 的那天起，团队就会开始挑简单的任务测、放宽判定、调参去迎合评委——分数涨了，系统没变好。防法是多指标互相牵制（成功率 + 成本 + 延迟 + 人工抽检），并且定期换一批没见过的测试题。

  • 闭环：跑评测集 → 看失败 trace → 归类 → 只改一处 → 再跑。
  • 回归门禁：分数、成本、延迟任一越线就拦住上线。
  • 古德哈特定律：指标成目标就失效，多指标牵制 + 定期换题。

要点回顾

这课记住什么

  • 成功率、成本、延迟三维一起看：成功率先写定义，成本按任务摊，延迟看 p99。
  • 判定成功三档串联：断言拦低级错，程序化检查验世界状态，打分补开放题。
  • 基准量的是整个系统：SWE-bench、GAIA、WebArena 能选模型，证明不了你的业务。
  • 自己的评测集是产品资产：真实任务 + 判定方法，进版本库、进 CI、当回归门禁。
  • 调参集与测试集分开：看过的题不能再当考试题；样本量决定可信度。
  • LLM-as-judge 先校准再信任：人类标签测一致率，双向跑、写死标准、换家族评委。
  • 观测是黑匣子：trace 记整次运行，span 记每步耗时、token、成本、错误。
  • 闭环改进 + 古德哈特定律：一次只改一处再跑评测集；指标成目标就失效，多指标牵制。
自测

你的 Agent 在 20 条自测题上成功率从 62% 涨到 81%，但这 20 条题你在调 prompt 时反复看过。最该怀疑什么？

A. 模型升级了，能力真的变强了
B. 样本太少、且测试集被调参污染，涨幅可能是运气加过拟合 ✓
C. 延迟变高了，成功率跟着涨
D. 成本降了，成功率自然涨
解析：20 条题的统计波动就有 ±20 个点，62% 到 81% 可能只是运气；更关键的是调参时看过测试集，等于开卷考试还抄了答案——分数涨了不代表真实任务上变好了。要换一批没见过的新题、扩大样本再测一次。
证据

论文与文章

  • SWE-bench: Can Language Models Resolve Real-World GitHub Issues?（Carlos E. Jimenez, John Yang, Alexander Wettig, Shunyu Yao, Kexin Pei, Ofir Press, Karthik Narasimhan，ICLR 2024 2024）
    支持：2,294 个真实 GitHub issue 任务，补丁须让仓库测试通过才算解决；发布时最强的 Claude 2 仅解决 1.96%；人工审核后的 Verified 子集为 500 题。
    边界：测的是整个系统（模型 + 支架 + 工具），不是模型单体；只覆盖 Python 仓库的修 bug 任务，不代表通用 Agent 能力。
  • GAIA: a benchmark for General AI Assistants（Grégoire Mialon, Clémentine Fourrier, Craig Swift, Thomas Wolf, Yann LeCun, Thomas Scialom，arXiv 2023）
    支持：466 道人工设计的通用助手问题，答案唯一可验证，需多步推理、上网与工具使用；人类 92%，带插件的 GPT-4 仅 15%；300 题答案不公开以支撑排行榜。
    边界：答案唯一、短答案为主，不覆盖开放式长任务；题目依赖的网络信息会随时间变化。
  • Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena（Lianmin Zheng, Wei-Lin Chiang, Ying Sheng, Siyuan Zhuang, Zhanghao Wu, Yonghao Zhuang, Zi Lin, Zhuohan Li, Dacheng Li, Eric P. Xing, Hao Zhang, Joseph E. Gonzalez, Ion Stoica，NeurIPS 2023 2023）
    支持：GPT-4 当评委与人类专家的一致率超 80%，与人类之间的一致率相当；同时发现位置偏差、啰嗦偏差、自我偏爱与推理能力有限四类问题，并给出换位复判等缓解方法。
    边界：结论来自 2023 年测试的模型版本；评委在数学与多步推理题上仍会误判，需先用人标样本校准再信任。
