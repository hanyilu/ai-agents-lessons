AI AGENTS 深入学习 · 第 12 天

后端工程：流式、异步与韧性五件套，让 Agent 在真实流量里活下来

Agent 循环一旦上线，拼的就不再是 Prompt，而是后端工程：一次任务可能跑几十秒到几分钟、调几十次模型与工具，任何一个环节没有超时、重试、幂等、限流与熔断兜底，都会在真实流量下变成重复扣费、线程耗尽或雪崩。流式是体验，异步是生存，五件套是底线。

2026-11-12 · 约 18 分钟
01 为什么是后端工程

Agent 不是一次请求，而是一段长任务。

前 11 天讲的都是 Agent 在一次运行里怎么思考、调工具、记东西。但上线后第一个撞上的问题不是智能，而是时间：一次带工具循环的任务很容易跑几十秒到几分钟，远超一次普通 HTTP 请求的舒适区。浏览器会超时、网关会掐连接、用户会以为卡死了。

所以后端工程的第一性原理是：把长任务从请求里拆出来。请求只负责接单与返回任务 ID，真正的工作由后台 Worker 异步执行，进展通过流式推送给前端。第二性原理是：故障是常态。模型服务会 429、会 5xx、会超时；网络会断；用户会重复点提交——超时、重试、幂等、限流、熔断不是锦上添花，是承重墙。

  • 同步请求只接单，Worker 异步执行，SSE 推流反馈进展。
  • 故障是常态：429、5xx、超时、断线、重复提交、突发流量都要预先设计。
  • 五件套缺一面，系统在真实流量下就会塌一角。
02 SSE 流式

SSE：一条不断的 HTTP 响应，就是全部魔法。

SSE 没有新协议，它就是一个 Content-Type 为 text/event-stream、永不结束的普通 HTTP 响应。服务端按帧写数据：每帧以 data: 开头、空行结尾，还可以带 event: 事件名、id: 事件序号、retry: 重连间隔。浏览器用 EventSource 接，断线后自动重连并带上 Last-Event-ID，服务端据此续传。

Agent 场景下，流里不能只推 token。至少分五类事件：token 增量、工具调用开始、工具调用结束、观察结果摘要、完成或错误。前端靠事件类型画进度条、工具卡片与最终结果；只推 token 的流，用户看到的只是一串字在涨，不知道 Agent 在干什么。

Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

event: tool_call_start
data: {"id": 12, "tool": "search", "args": {...}}

event: token
data: {"id": 13, "delta": "结论是"}

event: done
data: {"id": 98, "run_id": "run_01"}
  • 帧格式：data: + 空行分隔，可带 event:、id:、retry:。
  • EventSource 自动重连并带 Last-Event-ID，服务端据此续传。
  • 流可能丢、重、乱序：id 去重 + 续传 + 落盘完整结果，三者缺一不可。
03 异步任务

异步任务：状态机是任务的唯一事实来源。

异步化的标准链路是：接口创建任务行（pending）并返回任务 ID → 入队 → Worker 取任务执行（running）→ 完成落盘（succeeded）或失败（failed）。任务表就是任务的状态机，状态流转只能前进；任何一步崩了，恢复时都从任务表里的状态继续，而不是凭内存猜。

Worker 取任务要原子化：多个 Worker 同时抢同一条任务会重复执行，用 FOR UPDATE SKIP LOCKED 或队列的可见性超时保证一次只被一个 Worker 持有。Worker 崩溃或超时后，任务要在可见性超时后回到队列被别人重取；重取意味着可能重复执行，所以执行体必须幂等。

CREATE TABLE runs (
  id TEXT PRIMARY KEY,
  status TEXT CHECK (status IN (
    'pending','running','succeeded','failed','cancelled')),
  idempotency_key TEXT UNIQUE,
  result JSONB, error TEXT,
  updated_at TIMESTAMPTZ NOT NULL
);
  • 任务状态机：pending → running → succeeded / failed / cancelled，只能前进。
  • 取任务要原子化：SKIP LOCKED 或可见性超时，避免多 Worker 重复执行。
  • 事务发件箱：业务数据与事件同事务提交，中继进程负责投递。
04 超时

超时：没有超时，就没有上限。

超时要分层设，每一层守自己的边界：连接超时（建连多久没通就放弃）、读超时（发完请求多久没回包就放弃）、单步超时（一次模型或工具调用的上限）、总预算（整个任务从接单到结束的上限）。只设客户端超时、不设服务端超时，等于只锁了前门——服务端线程与连接池照样被挂起的调用占满。

超时值不要拍脑袋：按可接受的误超时率取下游延迟的分位——比如允许 0.1% 的调用被误杀，就取 p99.9 延迟作超时。总预算要往下游传：入口算出 deadline，每次调下游把剩余时间带上，下游按剩余时间设自己的超时。超时还要联动取消，否则只是前端不等了，后台还在烧钱跑。

  • 分层设：连接、读、单步、总预算，每层守自己的边界。
  • 客户端超时 ≠ 服务端超时，两边都要设。
  • Deadline 往下游传：下游按剩余时间设超时，不各设各的。
05 重试

重试：只重试瞬时错，且只在一层重试。

可重试的错只有三类：429（被限流）、408（请求超时）、5xx 与网络异常。4xx 里的其余错误（参数错、鉴权错、校验错）重试一百次也一样错，只会浪费配额。模型返回了内容但内容错了（工具参数非法、格式不对）——那是业务层纠错，靠循环里的校验与重提，不是靠 HTTP 重试。

重试是“自私的”：每一次重试都在已经吃力的依赖上再加一份负载。所以退避要用指数退避加抖动：等待时间按 1 秒、2 秒、4 秒指数增长，再加随机抖动打散同步的重试波。还要设上限——最大重试次数、最大退避、总时限，三者至少有两个。最危险的是分层重试放大：五层调用、每层重试 3 次，底层看到的负载最高可达 243 倍。

  • 只重试 429 / 408 / 5xx / 网络异常；其余 4xx 不重试。
  • 指数退避 + 抖动 + 上限：次数、退避、总时限缺一不可。
  • 分层重试会放大：五层各 3 次，底层最高见 243 倍负载。

06 幂等

幂等：重试的前提，是重做不产生副作用。

幂等的定义很简单：同一操作执行一次和执行多次，效果一样。GET、PUT、DELETE 天然幂等；POST 一般不幂等——所以 Agent 里所有有副作用的操作（扣费、发消息、写库、调外部 API）都需要显式做幂等，否则一次超时重试就可能扣两次费、发两条消息。

标准做法是幂等键：客户端为每一次逻辑操作生成一个唯一键（UUID），随请求带上；服务端用键 + 请求指纹（参数哈希）查表。第一次执行：写 pending 占位 → 执行 → 写 done 与结果；重试带同键同参数：直接返回第一次的结果，不再执行；同键不同参数：报错，拒绝复用。并发靠唯一约束或分布式锁保证只有一个真正执行。

  • 副作用操作必须幂等：扣费、发消息、写库、调外部 API 都算。
  • 幂等键 + 请求指纹：同键同参返回旧结果，同键不同参报错。
  • 超时歧义时：拿原键查结果，不要发新请求。

07 限流与熔断

限流守入口，熔断治持续故障。

限流算法里，Agent 服务的入口一般选令牌桶：桶里攒令牌、请求消耗令牌，桶满时多余令牌丢弃——允许短时突发、长期守平均速率。公式只有一行：tokens = min(容量, tokens + 速率 × 经过时间)。容量决定能扛多大的突发，速率决定长期平均。分布式下读令牌数与扣令牌数必须是原子操作，用 Redis + Lua 包成一次执行。

重试治瞬时故障，熔断治持续故障。熔断器三态：Closed 正常放行并计数失败；失败率越过阈值跳 Open，直接拒绝、不再发请求；冷却后进 Half-Open，只放一个探测请求，成功回 Closed、失败回 Open。熔断打开后必须有降级：便宜模型、缓存答案、跳过非关键工具——没有降级的熔断，只是把慢失败变成了快失败。

# 令牌桶：容量定突发，速率定平均
tokens = min(capacity, tokens + rate * elapsed)
if tokens >= 1:
    tokens -= 1  # 原子执行：Redis + Lua
    allow()
else:
    reject(429, Retry-After)
  • 分层限流：用户、租户、全局、下游四层都要有；429 必须带 Retry-After。
  • 熔断打开时不重试；半开只放一个探测请求。
  • Agent 循环内部也要有调用预算，否则限流只限了入口。
08 组合与落地

把五件套装进一条请求链。

单点机制都懂了，真正的工程在组合。一次典型请求链是：用户请求 → 网关限流（令牌桶）→ 创建任务并入队（发件箱保证不丢）→ Worker 执行循环，每步带超时、带幂等键调工具、可重试错只在 Worker 层重试一次 → 失败率越阈值时熔断打开、走降级 → 进展经 SSE 推流，断线续传靠事件 id → 完成落盘，任务状态机到终态。

组合时有两条全局约束。第一，总预算：入口定 deadline，全链路共享，每层按剩余时间设超时；重试消耗的也是总预算的一部分，不能无限重来。第二，可观测：每次重试、熔断跳变、限流拒绝都要打点，否则出问题时连哪一环在挡流量都看不出来。

  • 落地顺序：状态机与幂等键 → SSE + Worker → 超时/重试/限流/熔断 → 降级与可观测。
  • 验收四问：可恢复？不重复？降级还是雪崩？突发时哪层先拒绝？
  • 面试考场景题：重复提交、断线续传、持续 5xx，每题都是一组机制组合。
要点回顾

这课记住什么

  • 长任务要拆出请求：同步接单、异步执行、流式反馈，三者分工先定。
  • SSE 是不断的 HTTP 响应：事件分类型、带单调 id、断线续传，落盘才是事实。
  • 异步任务靠状态机：任务表是唯一事实来源，取任务原子化，执行体必须幂等。
  • 超时分层设、deadline 往下游传、超时联动取消，否则只是前端不等了。
  • 只重试瞬时错、只在一层重试、带指数退避与抖动，分层重试会把负载放大到 243 倍。
  • 幂等键 + 请求指纹 + 唯一约束：同键同参返回旧结果，超时歧义先查结果再重试。
  • 限流用令牌桶：容量定突发、速率定平均，分层限流，429 带 Retry-After。
  • 熔断治持续故障：Open 期直接拒绝 + 降级接管，没有降级的熔断只是快失败。
自测

Agent 任务里有一次扣费操作，第一次请求超时、不知道扣没扣。按本课的做法，后端最该怎么做？

A. 直接发一笔新扣费请求，失败了再人工退款
B. 拿原来的幂等键先查结果，查不到再按原键重试 ✓
C. 把重试次数调到最大，让请求自己恢复
D. 关闭重试，断线就让用户重新下单
解析：超时只说明响应丢了，不说明没执行。拿原幂等键先查结果：查到了直接返回，查不到按原键重试，服务端凭键去重；发新请求会扣两次，调大重试只会放大重复。
证据

论文与文章

  • Timeouts, retries, and backoff with jitter（Marc Brooker，Amazon Builders' Library 2019）
    支持：每一次远程调用都要设超时（含连接与读超时），按可接受的误超时率（如 0.1%）取下游延迟的对应分位作超时值；重试是“自私的”——只在依赖看起来健康时重试、重试无改善就停；分层重试放大：五层各重试 3 次，底层负载可达 243 倍；退避要加抖动打散同步重试波；每个客户端用令牌桶限制自己的重试量。
    边界：亚马逊内部实践总结，超时分位与重试预算是方法论而非放之四海的数值，需按自己的依赖延迟与预算调参。
  • Idempotent requests（Stripe，Stripe API Reference 2025）
    支持：幂等键机制：客户端生成唯一键（建议 V4 UUID），服务端保存第一次请求的响应（含 500 错误），同键重试直接返回保存的响应；同键不同参报错；v1 键至少保留 24 小时；GET/DELETE 天然幂等，不用带键。
    边界：这是 Stripe v1 的行为；v2 在窗口内不重复成功操作，细节以文档为准；键保留期与错误语义是 Stripe 实现，不代表所有系统。
  • HTML Standard: Server-sent events（WHATWG，WHATWG HTML Standard 2025）
    支持：SSE 帧格式（data:/event:/id:/retry: 字段、空行分隔）、text/event-stream；客户端断线重连时带 Last-Event-ID，服务端据此续传；事件流始终按 UTF-8 解码。
    边界：规范只定义格式与重连语义，不保证不丢、不重、不乱序；去重与落盘为准仍需应用层实现。
