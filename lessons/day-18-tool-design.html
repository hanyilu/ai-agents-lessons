AI AGENTS 深入学习 · 第 18 天

工具设计：模型不看你的代码，只看你的文档

工具是 Agent 的手，但模型看不到你的实现代码，只能看到名字、描述、参数表这三件套——这份文档就是模型与系统之间的全部接口（Anthropic 叫它 ACI，Agent-Computer Interface）。设计工具不是包一层 API，而是写一份让概率模型挑得准、填得对、错了能自己改回来的契约：名字像动词、描述第一句写边界、参数防呆收窄、错误写成反馈、副作用上锁；工具多了按需加载，跨系统用 MCP 统一接头。

2026-11-18 · 约 18 分钟
01 问题

模型的手好不好使，取决于你怎么写工具

第 8 天讲过：模型只生成调用意图，执行在后端。但还有另一面没讲——模型看得到什么？它看不到你的实现代码：查库的 SQL、鉴权、重试、缓存，全被挡在工具定义外面。

模型看到的只有三件套：工具名、一段描述、一张参数表。这份文档就是它与真实世界之间的全部接口——Anthropic 给它起了个名字：ACI，Agent-Computer Interface，Agent 版的人机界面。

  • 工具 = 模型的手，但手长什么样由文档决定。
  • ACI 的地位与 HCI 相当：给人用的界面要精心设计，给模型用的也一样。
  • 第 8 天讲模型侧怎么选；今天讲提供侧怎么写。
02 契约三件套

名字、描述、参数表，一件都不能含糊

契约第一件是名字：模型选工具是在工具名上算概率，名字就是检索信号。动词短语最稳——search_orders、refund_order；别让两个工具叫近义词，search、lookup、query 摆在一起，模型只能靠猜区分。

第二件是描述，第三件是参数表：描述讲清这工具是干什么的、什么时候用、什么时候别用；参数表画好格子——哪个必填、什么类型、只能取哪些值。描述里还要写返回值长什么样、有没有副作用。

  • 名字是概率的锚点：含糊的名字，选错是必然。
  • 描述第一句就要写清使用边界，别只写功能。
  • 参数表是格子，不是建议：必填、类型、枚举，一格都不能含糊。

03 描述写法

描述是写给模型看的检索信号

好描述有固定配方：第一句写“什么时候用、什么时候不用”；接着写输入格式与边界——order_id 是什么样、日期写哪种格式；再写返回值与副作用——返回什么、会不会改数据。

描述里还能放例子与边界情况：一个正确调用的例子，胜过三行抽象说明。Anthropic 的做法是把工具定义当给初级开发者的文档写——例子、边界、输入格式要求，一个都不能省。

  • 第一句定边界：用与不用，先讲清楚。
  • 例子是最好的描述：一个正确调用胜过抽象说明。
  • 描述太长也要付 token 钱：写全，但别写废话。
04 粒度

一个工具干一件事：Unix 哲学

工具太大，模型不敢调、调错了全错：一个 manage_order 又查又改又退，模型分不清这次该干哪一半，测试也难写。工具太小，简单任务要串五六步：每步都是一次调用、一次等待、一次出错的机会，账单跟着步数乘。

判断标准很简单：一次调用的结果能不能独立验证。查得到、改得对、退得了，每一步都有明确的成功信号，粒度就合适。后端类比：这就是 Unix 的“一个程序做好一件事”，也是微服务拆分的同一道题。

  • 太大：职责不清，调错全错，难测。
  • 太小：步数乘账单，中间状态多。
  • 标准：一次调用的结果能独立验证。
05 参数防呆

防呆：让模型想错都难

参数设计的第一原则是防呆（poka-yoke）：把容易错的格式收进工具内部，别让模型猜。Anthropic 的 SWE-bench 故事就是例子——模型总在相对路径上栽跟头，改成强制绝对路径，问题直接消失。

具体做法：必填收窄到最少、枚举代替自由文本、默认值取最安全的那档（默认只读、默认小范围）；单位写死——金额用分、时间用 ISO 格式；自然语言日期让工具内部解析，别让模型拼字符串。

  • 相对路径改绝对路径：格式问题在工具内解决。
  • 枚举收窄选择：自由文本是选错的温床。
  • 默认值取最安全档：默认只读、默认小范围。
06 错误即反馈

错误信息是模型唯一的反馈通道

模型调错了参数，唯一能学到的东西就是你返回的错误。只回“参数错误”四个字，模型改不对——它不知道错在哪、该怎么改。错误要写成给模型的提示：错在哪个字段、期望什么格式、今天是几号、合法值有哪些。

第 8 天的分层兜底在这里收口：解析层、schema 层、语义层拦下的错，每一层都要把错因写清楚再回填。回填不是认错，是给模型下一次调用的输入——写得越具体，自我修正的成功率越高。

  • 错因 + 期望格式 + 当前事实，三件套缺一不可。
  • 不要只回 400：模型看不懂状态码。
  • 错误回填是输入，不是道歉：为下一次调用服务。
07 规模与标准

工具多了按需加载，跨系统用 MCP 统一接头

工具清单进提示是要付 token 钱的：第 8 天算过，每个定义几百 token，50 个工具光清单就上万 token，又贵又挤内容，选错率也跟着涨。做法是按需加载：平时只留一个搜工具的元工具，用时再把具体定义取回来。

跨系统还有一层问题：每个数据源各写一套接头，N 个应用 × M 个数据源就是 N×M 份集成。MCP（模型上下文协议）把接头标准化：2024 年 11 月由 Anthropic 开源，2025 年 12 月捐给 Linux 基金会旗下机构；它分三件——工具（模型调）、资源（只读数据）、提示词（模板），各接一次就能任意组合。

  • 清单是成本：按需加载，用时再取。
  • MCP 把 N×M 份集成变成 N+M。
  • MCP 不管认证与审计：那些还在实现层。

MCP 不发明新能力，它只统一接头：接头标准化之后，工具定义本身仍要按本课的契约写。

08 落地

落地：工具设计检查清单

新工具上线前过一遍清单：名字是不是动词短语、有没有近义词撞车；描述第一句写没写边界；参数有没有收窄、默认值安不安全；副作用工具有没有确认门与幂等键；错误信息能不能让模型自己改对。

最后是读与写的分界：查数据的工具与改数据的工具分开命名、分别授权；改数据的默认走确认或 dry-run（试运行）——先算一遍给模型看，确认了再真执行。工具设计不是包一层 API，是给不可靠的调用方写一份可靠的契约。

def search_orders(order_id: str, ...):
    """按订单号查订单状态与物流。

    何时用：用户问订单到哪了、多少钱、包含什么。
    何时不用：退款、改地址、取消订单——用专用工具。
    参数：order_id 形如 ORD-2026-000123，不存在会返回
    NOT_FOUND（不要猜一个编号重试）。
    只读：不改任何数据。
    """
    ...
  • 清单五问：名字、边界、参数、副作用、错误。
  • 读与写分开：改数据的默认确认或试运行。
  • 上线前拿真实任务跑几遍：看模型实际怎么调。
要点回顾

这课记住什么

  • 模型看不到你的代码，只能看到名字、描述、参数表——这份文档就是 ACI，Agent 与系统的全部接口。
  • 名字是概率的锚点：动词短语、别撞近义词；描述第一句写清何时用、何时不用。
  • 描述按配方写：边界、输入格式、返回值、副作用，再加一个正确调用的例子。
  • 粒度按 Unix 哲学：一个工具干一件事；标准是一次调用的结果能独立验证。
  • 参数防呆：格式收进工具内、枚举收窄、默认值取最安全档；Anthropic 把相对路径改成绝对路径，问题直接消失。
  • 错误是模型唯一的反馈：写清错因、期望格式与当前事实，回填给模型重试。
  • 副作用工具要上锁：读与写分开命名，改数据的走确认门、幂等键或 dry-run。
  • 工具多了按需加载；跨系统用 MCP 统一接头，把 N×M 份集成变成 N+M；但 MCP 不管认证审计，契约本身仍要自己写好。
自测

客服 Agent 有两个工具：get_order 查订单，refund_order 退款。模型经常在用户只问“我的订单到哪了”时就调 refund_order。按本课的做法，最该先改什么？

A. 在提示词里加粗写“不许随便退款”
B. 把 refund_order 的描述第一句写清“仅用户明确要求退款时用；只查询不用它”，并给退款加上人工确认门 ✓
C. 把两个工具合并成一个 order_tool，省 token
D. 把模型换成更大的
解析：描述是检索信号：选工具是在工具名上算概率，描述第一句写清边界才能把查询与退款分流；退款是不可逆副作用，确认门必须长在执行层，不能只靠提示词。合并工具会让粒度变粗、更难选；换模型不解决契约问题。
