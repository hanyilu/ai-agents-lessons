AI AGENTS 深入学习 · 第 11 天

编排框架：把 Agent 循环写成一张可恢复的状态图

第 9 天的 ReAct 循环是一条 while 循环：想、动、看、再想。写死在代码里能跑，但一上线就缺三样东西：状态丢了怎么续跑、循环失控谁叫停、敏感动作谁点头。编排框架回答这三个问题：把循环画成一张状态图——节点是干活的函数、边是走哪条路的规则、状态是全图共享的一本账；再给图装上检查点（每步存盘）、中断点（到点停下等人批）和子图（一个节点里再装一张图）。单 Agent 还是多 Agent，取舍不在“多就强”，而在复杂度放进一个循环里，还是拆成几张图之间传消息：拆开能并行、能分工，但每多一次交接就多一次幻觉放大的机会、多一份账单。

01 为什么循环要画成图

while 循环能跑，但加功能时先散架。

ReAct 循环写成 while 循环没问题，直到你要加功能：跑到一半进程挂了怎么续、循环转了 40 圈还没停谁管、发邮件前要不要先让人看一眼。while 循环里这些全是散落的 if 和全局变量，改一处牵全身。

状态图把控制流从代码里抽出来、写成数据：节点、边、状态三件套摆在纸面上，执行器按图走。好处是控制流变得可见、可检查、可画出来——也就能断点续跑、能暂停、能回放。后端类比：订单状态机，状态转移写在表里而不是散在 if 里。

  • while 循环能跑，但加断点续跑、暂停、回放要重写。
  • 状态图把控制流写成数据，执行器按图走。
  • 图是后端状态机的老办法，不是新发明。
02 三件套：状态、节点、边

状态是账本，节点是干活的，边是裁决的。

状态（State）是一张全图共享的表，通常写成 TypedDict：消息列表、已做步骤、待办事项都在里面。节点（Node）是函数，读状态、干活、返回“改了哪几项”——不直接改整张表，改动由 reducer 合并，比如消息列表是追加不是覆盖。

边（Edge）决定下一步去哪：固定边永远从 A 到 B；条件边跑一个确定性函数，看一眼状态、返回下一个节点的名字。关键分工：模型只在节点里提议（写什么、调哪个工具），去向由代码裁决——第 9 天“模型提议、代码裁决”的护栏，在这里落成一张图。

graph = StateGraph(AgentState)
graph.add_node("agent", call_llm)
graph.add_node("tools", ToolNode(tools))
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", route, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")
app = graph.compile(checkpointer=checkpointer)
  • 状态是全图共享的一本账，只放流转必需的。
  • 节点返回增量，reducer 决定怎么合并。
  • 条件边是确定性函数，别在里面调模型。

03 循环怎么转、怎么停

终止条件写进边里，步数上限是硬刹车。

循环就是一条回到起点的边：tools → agent，再由条件边决定继续还是结束。终止条件必须写进条件边里——最常见的是“模型没再调工具就 END”，再加一道硬护栏：步数上限，超了强制 END。

循环要转得有意义，每圈状态必须变：新消息、新工具结果追加进来，模型看到的东西和上一圈不一样。如果状态原地不动，模型会一模一样地再调一次工具——第 9 天的重复检测，就是发现“这一圈和上一圈长得一样”时直接刹车。

  • 终止条件写进条件边，别只靠模型自觉停。
  • 步数上限是最后一道刹车。
  • 每圈状态必须变，否则就是原地打转。
04 检查点：每步存盘

崩了能续跑，还能回到任意一步重跑。

编译图时挂一个 checkpointer，每跑完一个节点，整份状态就存一份快照。进程崩了、机器重启了，拿 thread_id 把快照捞回来，从断的那一步接着跑，已完成的节点不重跑——这就是第 1 轮第 17 天讲的断点续跑，在图里是现成的。

快照还能“时间旅行”：回到任意一步、改一点状态、从那重跑，排障时不用从头复现。注意和第 10 天的记忆区分：检查点存的是执行状态（跑到哪了），记忆存的是业务事实（用户喜欢什么）；一个管续跑，一个管召回。

  • 每步一存盘，崩了从断点续跑。
  • thread_id 隔离不同会话的快照。
  • 内存存盘只够演示，生产用 SQLite 或 Postgres。
05 中断点：敏感动作先停下

审批长在执行层，不在 prompt 里。

编译时声明 interrupt_before=["下单"]，图跑到下单节点前就停住：状态已经存盘，控制权回到你的代码。你在界面上把“要下的单”展示给人看，人点了批准，图从检查点原地续跑；点了拒绝，图走另一条边去取消。

这就是第 14 天要讲的安全的落地形态：审批长在执行层，不在 prompt 里。prompt 里写“下单前先问我”只是建议，模型可能忘了；中断点是图结构的一部分，模型绕不过去。代价是延迟：人在回路里，图要等多久都行——因为状态在盘里，不在内存里。

  • 中断点是图结构的一部分，模型绕不过去。
  • 批了从检查点续跑，拒了走另一条边。
  • 人在回路里，图等得起，因为状态在盘里。

06 单 Agent 还是多 Agent

拆开能并行、能分工，但每次交接都可能放大幻觉。

一个 Agent 干所有活，天花板来得很快：工具一多，选工具的准确率就掉（第 8 天）；上下文一长，中间信息就被忽略（第 1 天）。拆成多 Agent，就是把活分给几张图：Supervisor 一张图调度、工人各干一摊，最后合成。分工的收益是并行与专注：三个工人同时查三份资料，比一个 Agent 串行查快。

但拆分的代价要先算清：每多一个 Agent 就多一次 LLM 调用，账单与延迟都涨——Anthropic 的原话：Agent 拿延迟和成本换任务表现。每多一次交接就多一次幻觉放大的机会：上游编了个错数字，下游照单全收，还写得更自信。常见拓扑有三种：Supervisor（中心调度）、流水线（固定链）、并行投票（多跑几遍再汇总）。

  • 拆的前提：任务能干净拆分，或子任务真能并行。
  • 拆的代价：调用次数、延迟、交接处的幻觉级联。
  • 先单后多：复杂度只有可证明的收益才加。
07 常见坑与落地

state 别成垃圾场，路由别调模型，交接要验货。

第一，state 别变成垃圾场：只放流转必需的（消息、步骤、待办），业务数据放外部存储、state 里只放指针——第 10 天的教训在这里一样适用，state 一大，每步存盘都贵、每次进模型都贵。

第二，条件边里别调模型：路由函数要确定性、可测试，调了模型就等于把控制流又交回概率里，出了问题复现不了。第三，子图之间传消息要定契约：输入输出写成 schema，交接点加校验门——上游的输出先验一遍再进下游，别让幻觉顺着边往下流。

  • state 只放流转必需的，业务数据放外面。
  • 路由函数确定性、可测试，别调模型。
  • 交接点定 schema 加校验，防幻觉顺边下流。
要点回顾

这课记住什么

  • 编排框架把 ReAct 循环画成状态图：节点干活、边定去向、状态是全图共享的一本账。
  • 状态是 TypedDict，节点返回增量、reducer 合并；条件边是确定性代码，看状态返回下一个节点。
  • 控制流分两层：模型在节点里提议，代码在边上裁决——模型决定不了自己去哪。
  • 循环的终止条件要写进条件边，再加步数上限当硬刹车；每圈状态必须变，否则原地打转。
  • 检查点每步存盘：崩了从断点续跑，还能回到任意一步改状态重跑；thread_id 隔离会话。
  • 中断点把审批长在执行层：敏感动作前停下，批了从检查点续跑，拒了走另一条边。
  • 多 Agent 的收益是并行与分工，代价是调用次数、延迟与交接处的幻觉级联。
  • 先单后多：Anthropic 的建议是复杂度只有可证明的收益才加；拆之前先问任务能不能干净拆分。
自测

Agent 要“查库存 → 下单 → 发邮件通知用户”，下单不可逆。按本课讲的编排，正确的做法是？

A. 三步全写进一个 prompt，让模型自己决定顺序和时机
B. 图里在下单节点前加 interrupt_before，人批了再从检查点续跑 ✓
C. 下单失败就让模型无限重试，直到成功为止
D. 查库存、下单、发邮件拆成三个 Agent，各自独立跑
解析：不可逆动作要把审批长在执行层：interrupt_before 让图在下单前停住、状态存盘，人批了从检查点续跑、拒了走另一条边。只写进 prompt 是建议，模型可能忘了；无限重试没有刹车；三步拆三个 Agent 既无并行收益、又多两次交接，不值得。
