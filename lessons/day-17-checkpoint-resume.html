断点续跑：长任务中断后，凭什么不从头重跑

断点续跑不是“记住对话”，而是一套可恢复的执行契约：检查点定下恢复边界，thread_id 定下恢复身份，幂等与补偿定下重放的安全性；三者缺一，长任务在崩溃、部署或人工等待后都会以重复副作用或丢状态的方式还账。

2026-11-17 · 约 18 分钟
01 问题

长任务最怕的不是慢，是断

Agent 任务短则几十秒，长则几小时：中间要调几十次模型、查库、发请求。进程随时可能崩，部署随时会重启，敏感动作还要停下来等人批。

没有断点续跑，每次中断都只能从头重跑：前面的模型调用白花钱，更糟的是副作用会重复——退款发两次、工单建两份。

  • 中断分三种：崩、部署、等人。
  • 从头重跑的代价：钱 + 重复副作用。
  • 断点续跑要回答：从哪接上、重跑什么才安全。
02 检查点

检查点：超步边界的状态快照

检查点是图状态在超步边界的快照：每跑完一步，框架把全部状态写进持久存储。超步就是图的一次“心跳”，这一拍里排到的节点都跑完，才写一张快照。

后端类比：像数据库的事务提交点，也像游戏存档点。内存里的状态进程一死就没了，落盘的快照才能跨进程、跨部署活下来。

  • 一张快照 = 一拍结束时的全部状态 + 下一步跑谁。
  • 快照写进数据库（SQLite/Postgres），不是放内存。
  • 没有检查点，恢复无从谈起。
03 身份

thread_id：恢复用的游标

thread_id 是检查点的组织方式：同一个 thread 下的所有快照排成一条链，恢复就是沿着这条链找到最新一张。换个 thread_id，就是一条全新的链、空状态。

类比后端：像订单号，也像会话 ID。调用时必须带上它，框架才知道该读谁的快照、该把新快照存到哪条链上。

  • thread_id 是主键：没它存不下、也续不上。
  • 同一 thread 续跑，新 thread 从零开始。
  • thread_id 要稳定、不要放敏感信息。
04 恢复

恢复时发生什么

崩了之后再调一次，框架读最新快照、从下一个节点继续。已完成的节点不重跑：同一超步里先完成的节点，它的写已被存成 pending writes，恢复时直接复用。

但进行中的节点没有完整快照，只能从头重跑。恢复的边界就卡在这里：已完成的不动，进行中的重来。

  • 已完成节点：结果已落盘，跳过。
  • 进行中节点：没有快照，从头重跑。
  • 恢复 = 读快照 + 跳过 + 重跑，一次调用完成。

05 效应缺口

效应缺口：重跑的代价在副作用上

重跑最大的坑不在状态，在副作用。节点在发完退款、还没跑完就崩了：恢复时节点从头重跑，退款会再发一次。状态恢复了，外部世界却多了一次效应。

这段缺口叫效应缺口：副作用已提交、节点未完成。补法有三：工具带幂等键，同一 key 重放只生效一次；或把副作用拆成独立节点；或移到 interrupt 之后。

  • 状态能回滚，外部效应回不了。
  • 幂等键是标准答案：重放多少次，结果一次。
  • 拆节点、后移副作用，都是缩小缺口的办法。

06 审批绑定

审批绑定：interrupt 的三条规矩

interrupt 是动态暂停点：调到它就存快照、无限期等外部输入，恢复时用 Command 把答案送回，变成这次 interrupt 的返回值。

关键规矩：恢复时整个节点从头跑，interrupt 之前的代码会再执行一遍。所以 interrupt 之前只放纯计算，副作用放它之后；多个 interrupt 顺序不能乱，恢复值按顺序配对。

  • 节点从头重跑，interrupt 前的代码再跑一遍。
  • 副作用放 interrupt 之后，或做成幂等。
  • 别把 interrupt 包进 try/catch，暂停信号会被吞掉。
07 三档持久化

持久化三档：速度与保证的取舍

LangGraph 给了三档 durability：exit 只在退出时写一次，最快，但中途崩了什么都没留下；async 边跑边异步写，快且较稳，崩的瞬间仍可能丢一张；sync 每步写完再走，最稳，也最慢。

后端类比：像写日志时调不调 fsync。选哪档看任务：能重跑的批处理用 exit，跑几小时的长任务用 sync，中间态默认 async。

  • exit：只写退出时，崩了没记录。
  • async：边跑边写，小概率丢一张。
  • sync：步步落盘，最稳最慢。
08 落地

落地：检查点清单与恢复骨架

落地四件套：选对后端——内存只够开发，单机用 SQLite，生产用 Postgres；thread_id 一个任务固定一个；工具全带幂等键；敏感动作放 interrupt 后面。

最后一件是过期：默认每步写全部状态，快照会越攒越大、越攒越贵。只存增量的 DeltaChannel 能瘦身，长线程还要定保留策略：留多久、删多旧。

from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    graph = builder.compile(checkpointer=checkpointer)

# 一个任务固定一个 thread_id：它就是恢复的游标
config = {"configurable": {"thread_id": "order-4821"}}

# 崩了 / 等人批之后，同一 thread 再调一次就是续跑
graph.invoke(None, config)                  # 出错后：从最新检查点续跑
graph.invoke(Command(resume=True), config)  # 批了：被中断节点从头再跑

# 工具里用幂等键：同一 key 重放多少次，外部只生效一次
  • 后端按环境选：内存 < SQLite < Postgres。
  • 幂等键 + interrupt 审批，是上线前的两道门。
  • 快照会膨胀：定保留策略，别只写不删。
要点回顾

这课记住什么

  • 长任务一定会断：崩、部署、等人批，断点续跑不是加分项，是上线条件。
  • 检查点是超步边界的状态快照，落盘才能跨进程恢复；内存里的快照进程一死就没了。
  • thread_id 是恢复的身份：同一 thread 续跑，新 thread 从零开始。
  • 恢复时已完成的节点不重跑，进行中的节点从头重跑——边界就卡在这里。
  • 状态能恢复，外部副作用不能：节点在副作用后、完成前失败，重跑会重复效应，这就是效应缺口。
  • 补缺口三招：幂等键、把副作用拆成独立节点、把副作用移到 interrupt 之后。
  • interrupt 恢复时整个节点从头跑：interrupt 之前只放纯计算，副作用放后面。
  • durability 三档是速度与保证的取舍：exit 最快最险，sync 最稳最慢；快照会膨胀，保留策略要先定。
自测

一个四步任务，检查点在每步后都写了。跑到第 3 步时进程崩了，第 3 步已经发了一次退款。恢复后会发生什么？

A. 从第 1 步全部重跑，退款再发一次
B. 第 1、2 步跳过，第 3 步从头重跑，退款可能再发一次 ✓
C. 直接从第 4 步继续，第 3 步算完成
D. 恢复失败，只能新建一个 thread 从头跑
解析：检查点只保已完成的步骤：第 1、2 步的结果已落盘，跳过；第 3 步没有完整快照，只能从头重跑。它发过的退款在恢复时会再发一次，除非工具带了幂等键。
证据

论文与文章

  • Checkpointers（LangChain，LangChain Docs 2026）
    支持：检查点在每个超步边界保存图状态快照并按 thread 组织；超步内已完成节点的写会被保留为 pending writes，恢复时不重跑；三种 durability 模式 exit/async/sync 的取舍；默认每个超步写全部通道值，DeltaChannel 只写增量。
    边界：官方文档，描述当前 LangGraph 行为；具体 API 与默认值可能随版本变化，落地前需以所用版本文档为准。
  • Interrupts（LangChain，LangChain Docs 2026）
    支持：interrupt 会保存图状态并无限期等待，直到用同一 thread_id 以 Command 恢复；恢复时整个节点从头重跑，因此 interrupt 之前的副作用必须幂等，或移到 interrupt 之后、拆成独立节点。
    边界：官方文档，描述当前 LangGraph 行为；不同语言 SDK 的 API 细节可能有差异。
